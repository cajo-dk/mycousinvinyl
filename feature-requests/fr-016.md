# Feature Request

- REQUEST ID: FR-016
- DATE: 2026.02.28

## Abstract

Improve UX for phones and tablets in portrait orientation while preserving the current desktop/landscape experience.

## Scope

- Frontend: responsive behavior based on device type and orientation.
- UX: portrait-optimized header and list item actions.
- Access/Security: no changes to roles, permissions, or RBAC behavior.

## Requirements

### Device Type and Orientation Detection

- The UI must determine device type (phone/tablet/other) and current orientation (portrait/landscape).
- UX behavior must adapt at runtime when orientation changes without requiring a page reload.
- If device type and/or orientation cannot be determined, the app must use the current UX behavior as a safe fallback.

### Portrait List Item Actions

- In portrait list views, commonly used line-item actions (at minimum `View` and `+1` where applicable) must be directly available as individual buttons.
- Less frequently used actions should be grouped into a compact overflow menu accessed via a hamburger/menu icon.
- This behavior applies to list/table-like views where row actions are currently available and space is constrained.

### Portrait Header Label

- In portrait mode, shorten the application title in the header from `MyCousinVinyl` to `MCV` to reduce horizontal space usage.
- In landscape or fallback mode, keep the existing `MyCousinVinyl` label.

### Security / RBAC

- No changes to authentication, authorization, or RBAC.
- Existing role permissions (Admin/Editor/Viewer) remain unchanged.

## Non-Functional Expectations

- Orientation changes should feel immediate and stable, with no visible layout flicker.
- The responsive behavior should be reusable across pages instead of duplicated per component.
- Desktop and tablet landscape UX should remain functionally equivalent to current behavior.

## Acceptance Criteria

- On phones and tablets in portrait orientation, the UI uses portrait-optimized behavior.
- Switching between portrait and landscape updates the UX dynamically without a reload.
- If device/orientation detection fails, current UX is used with no regression.
- In portrait list views, `View` and `+1` are visible as direct row buttons (when the action is relevant), and secondary actions are available from a menu icon.
- In portrait mode, header title displays `MCV`; in non-portrait/fallback it displays `MyCousinVinyl`.
- No RBAC or role behavior changes are introduced.

## Edge Cases / Constraints

- Some views may not have a `+1` action; in those views, only applicable frequent actions are surfaced directly.
- Browser/device APIs can be inconsistent; detection logic must tolerate missing or partial signals and safely fall back.
- Orientation events may fire rapidly on some devices; updates should avoid redundant rerenders where practical.

## Implementation Plan (Draft)

### Current State Snapshot

- Portrait/coarse-device behavior already exists in parts of the UI via CSS media queries (not centralized logic).
- Existing portrait-specific list behavior is present in:
  - `frontend/src/pages/Collection.css`
  - `frontend/src/pages/Albums.css`
- Navigation already has separate full/short brand spans but both currently render `MyCousinVinyl`.
  - `frontend/src/components/Layout/Navigation.tsx`
  - `frontend/src/components/Layout/Navigation.css`

### Phase 1: Shared Responsive Context

- Create a reusable hook for runtime mode detection:
  - `frontend/src/hooks/useResponsiveMode.ts` (new)
- Hook output should include:
  - `deviceType`: `phone | tablet | other | unknown`
  - `orientation`: `portrait | landscape | unknown`
  - `isPortraitTouch`: boolean helper
  - `isFallback`: true when signals are missing/unsupported
- Detection signals:
  - `window.matchMedia('(orientation: portrait)')`
  - `window.matchMedia('(pointer: coarse)')`
  - viewport width breakpoints for phone/tablet inference
  - graceful fallback if APIs are unavailable
- Runtime adaptation:
  - subscribe to `matchMedia` change events and `resize` as fallback
  - debounce/throttle update handling to avoid rapid rerender loops on rotation

### Phase 2: Header Brand Behavior (`MyCousinVinyl` -> `MCV` in portrait)

- Update navigation brand rendering to use responsive hook:
  - `frontend/src/components/Layout/Navigation.tsx`
- Change short label span content to `MCV`.
- Apply conditional class/data attribute for portrait mode, while preserving existing desktop behavior.
- Update nav CSS to ensure short/long labels switch cleanly without layout jump:
  - `frontend/src/components/Layout/Navigation.css`

### Phase 3: Portrait Row Actions Pattern (Reusable)

- Create a reusable row actions component for compact portrait mode:
  - `frontend/src/components/UI/ResponsiveRowActions.tsx` (new)
  - `frontend/src/components/UI/ResponsiveRowActions.css` (new)
  - export in `frontend/src/components/UI/index.ts`
- Behavior:
  - primary actions rendered as direct buttons (e.g., `View`, `+1`)
  - secondary actions grouped behind a menu button (hamburger/overflow)
  - keyboard accessible menu open/close and focus behavior
  - closes on outside click and route change

### Phase 4: Apply Row Actions in List Views

- Collection list:
  - integrate `ResponsiveRowActions` in `frontend/src/pages/Collection.tsx`
  - keep `View` + `+1` as direct actions in portrait
  - move `Edit` and `Delete` to overflow menu in portrait
  - simplify portrait-specific hiding rules in `frontend/src/pages/Collection.css`
- Albums list:
  - integrate in `frontend/src/pages/Albums.tsx`
  - keep `View` as direct action in portrait
  - move less-frequent actions (`Add Pressing`, `Edit`, `Delete`) into overflow in portrait
  - update `frontend/src/pages/Albums.css` for consistent action layout
- Artists and Pressings:
  - evaluate and align action density with same pattern in:
    - `frontend/src/pages/Artists.tsx`, `frontend/src/pages/Artists.css`
    - `frontend/src/pages/Pressings.tsx`, `frontend/src/pages/Pressings.css`
  - no functional action changes, only responsive action placement

### Phase 5: Fallback and Safety Rules

- Ensure all responsive enhancements are additive:
  - if hook reports `unknown` or fails, render existing/current UX path
- Avoid replacing existing table flows on desktop/landscape.
- Keep all existing action handlers and API calls unchanged (frontend-only presentation refactor).

### Phase 6: Verification

- Automated:
  - `frontend` lint and test suite (if present)
- Manual matrix:
  - Phone portrait/landscape
  - Tablet portrait/landscape
  - Desktop
  - Simulated unsupported orientation/device APIs to validate fallback behavior
- Regression checks:
  - navigation, global search modal, and table row actions across Collection/Albums/Artists/Pressings

### Delivery Breakdown

- PR 1: shared responsive hook + header brand update.
- PR 2: reusable responsive row actions component + Collection integration.
- PR 3: Albums/Artists/Pressings action harmonization + polish + regression fixes.
